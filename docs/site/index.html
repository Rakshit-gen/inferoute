inferoute

An OpenAI-compatible inference gateway written in Go. Point your client at inferoute the same way you'd point it at OpenAI, and it round-robins requests across whichever LLM backends you give it (several Ollama or vLLM instances, or a hosted provider like Groq), fails over on error, streams responses through unbuffered, and optionally caches repeat requests so they never hit a backend twice.

inferouted

The inference engines (vLLM, SGLang, llama.cpp, Ollama) are a solved, crowded problem. The layer that routes to them (load balancing, failover, caching, observability) isn't, and it's infrastructure glue, which is what Go is for. inferoute is that layer: a single static binary, one JSON config file, no database of its own to run.

Install

One command (needs the Go toolchain, nothing else):

$ curl -fsSL https://raw.githubusercontent.com/Rakshit-gen/inferoute/main/install.sh | sh

That resolves straight to the latest commit on main via go install .../cmd/inferouted@latest, so there are no stale prebuilt-binary releases to maintain. Don't have Go? The script says so and points at go.dev/dl instead of failing silently. Prefer building from source instead: 

git clone https://github.com/Rakshit-gen/inferoute && cd inferoute
go build -o bin/inferouted ./cmd/inferouted

Run it locally

inferoute needs at least one backend to route to. The fastest way to see routing and failover actually happen is two local Ollama instances serving the same model: 

OLLAMA_HOST=127.0.0.1:11434 ollama serve &
OLLAMA_HOST=127.0.0.1:11435 ollama serve &
ollama pull llama3

config.example.json in the repo already points at both of those for llama3, so: 

$ inferouted -config config.example.json
inferouted: listening on :8081, routing to 2 backend(s)

Send it a request, in the same shape as the OpenAI chat completions API:

$ curl localhost:8081/v1/chat/completions \
    -d '{"model":"llama3","messages":[{"role":"user","content":"hi"}]}'
{"model":"llama3","message":{"role":"assistant","content":"..."}, ...}

That response came from whichever of the two Ollama instances inferoute picked, and you didn't have to know or care which. Kill one ollama serve process and send the request again: the next one fails over to the survivor instead of erroring. Check what inferoute currently thinks is healthy at any time: 

$ curl localhost:8081/v1/backends
[{"name":"ollama-1","url":"http://localhost:11434","healthy":true},
 {"name":"ollama-2","url":"http://localhost:11435","healthy":false}]
No Ollama handy? Point a backends entry at any OpenAI-compatible host instead: see api_key and path_prefix under Configuration for gatewaying a hosted provider like Groq without your callers needing their own key.

CLI

The binary is inferouted, and it has exactly one flag:

$ inferouted -config path/to/config.json   # defaults to ./config.json
$ inferouted -h                            # prints usage and exits

No subcommands, no interactive mode: it's a daemon. Point it at a config file, it starts listening, Ctrl-C (or SIGTERM) shuts it down cleanly. A SIGHUP reloads backends and model_aliases from the same file without restarting or dropping in-flight requests: 

$ kill -HUP $(pgrep inferouted)

Configuration

Everything lives in one JSON file (config.example.json is a working starting point). Every field has a sane default except backends, which is required.

FieldWhat it does
listen_addrWhere inferoute itself listens, e.g. :8081.
health_check_path, health_check_intervalPath to GET on each backend to check it's alive, and how often.
backends[].name, .url, .modelsServers to route to. models is the list of model names that backend serves; two backends listing the same model get load-balanced between.
backends[].path_prefixPrepended to the client's request path, for backends that mount their API under a path (Groq's OpenAI-compatible endpoint lives under /openai).
backends[].api_keySent as that backend's Authorization: Bearer header, overriding whatever the client sent, for gatewaying a hosted provider behind a key callers shouldn't need to know.
backends[].weightBiases the weighted load-balancing strategy toward beefier backends (default 1, ignored by the others).
load_balancingHow to pick a backend among the healthy ones for a model: round_robin (default), least_pending (fewest in-flight requests), or weighted (random, biased by weight).
rate_limit.enabled, .requests_per_second, .burstPer-API-key token bucket (Authorization: Bearer <key>, falling back to remote IP). Off by default.
rate_limit.redis_addrLeave empty for a per-instance limiter. Set to share limit state across a fleet of inferoute instances via Redis.
cache.enabled, .nucladb_addrSemantic response caching, backed by a running NuclaDB instance. Off by default.
cache.embedding_backend_addr, .embedding_modelOllama-compatible server and model used to embed prompts for cache lookups.
cache.max_distanceHow close a cached prompt has to be to count as a hit: see Semantic cache notes, the naming is easy to get backwards.
cache.tenant_idNuclaDB tenant inferoute's cache vectors are stored under.
model_aliasesMaps a requested model name to one your backends actually serve, e.g. {"gpt-4": "llama3"}.

Endpoints

Everything inferoute itself serves, beyond the proxied /v1/* routes:

RouteWhat it does
POST /v1/*Proxied to a backend: same path the client used, plus path_prefix if set. This is the actual gateway traffic.
GET /v1/modelsOpenAI-compatible model list: every model a backend serves plus every alias. SDKs call this to populate model pickers.
GET /v1/backendsJSON snapshot of every backend's name, URL, models, and current health.
GET /v1/configActive model aliases, health-check interval, and whether rate limiting, caching, and API-key auth are on.
GET /healthzLiveness probe: always 200 once the process is up.
GET /metricsPrometheus: request count by model/backend/status, latency histogram, cache hit/miss/error counts.
GET /docsThis page, served straight from the running binary.

Semantic cache notes

Two things that will silently misbehave if you get them wrong, found by actually running inferoute against a live NuclaDB instance rather than trusting the API docs:

Embedding dimension must match. NuclaDB is started with a fixed vector dimension for the whole database (nucladbd -dim); point cache.embedding_model at a model that produces vectors of that exact length, or inserts get rejected.
max_distance, not a similarity threshold. NuclaDB's cosine "score" is 1 - cosine_similarity: a distance, where 0 means identical and larger means further apart. A smaller max_distance means a stricter match, the opposite of what "similarity threshold" naming suggests, which is exactly the bug the first version of this cache had. Fixed by round-tripping identical and different prompts against a live server and checking the actual scores returned.

Streaming responses are cached too, not just JSON ones: a cached SSE stream is replayed as the exact bytes originally captured, confirmed via the X-Inferoute-Cache: hit response header on a hit.

Deploying it

Everything in the repo, not just the local path:

Docker
$ docker compose up --build

Starts inferoute plus two Ollama containers (docker-compose.yml, config in config.docker.json).

Render

Deploys straight from Dockerfile as a plain web service: health check /healthz, real config via a Secret File mounted at /etc/secrets/config.json. Full steps in the repo README's "Deploy to Render" section.
